⚠ Conflict: Who Wins?

💥
Same document ID — Firestore does last-write-wins. Whichever device's bridge writes last overwrites the other. No field-level merge.
👯
Different document IDs — If both devices generated UUIDs offline for the "same" logical action, you get duplicate documents.
🔢
Inventory counters — Ditto uses CRDT counters (merge-safe). Firestore uses plain integers. A decrement on Device A and Device B both read qty=50, both write qty=49. One decrement is lost.
🔄
Sync loops — Without careful change guards, the bridge can ping-pong updates between Firestore and Ditto indefinitely.
Possible Resolutions

Option A: Ditto as Source of Truth

Firestore is a cloud mirror. Ditto CRDTs handle all conflict resolution.

  • All reads from Ditto (CRDT merge is automatic)
  • Bridge pushes Ditto → Firestore with SET MERGE
  • No conflicts — Ditto resolves them
  • Firestore is eventually consistent
  • Firestore consumers see stale data during partitions

Option B: Firestore as Source of Truth

Ditto is transport-only. Offline writes queue and replay to Firestore on reconnect.

  • Offline writes marked "pending" in Ditto
  • On reconnect: replay to Firestore via transactions
  • Server-side conflict resolution (you build it)
  • Complex — essentially building your own sync protocol
  • Ditto P2P becomes a message bus, not a store

Option C: Split Authority Recommended

Each store owns different collections. No conflicts by design.

  • Firestore owns: products, menu, config (read-heavy, admin-managed)
  • Ditto owns: orders, inventory, cart (write-heavy, multi-device)
  • Bridge is one-directional per collection
  • No conflict resolution needed
  • Each store plays to its strengths
